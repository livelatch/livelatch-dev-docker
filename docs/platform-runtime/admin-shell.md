# Admin Shell

A `/admin/shell` page that runs a single shell command **inside the running Railway container** and streams stdout/stderr back to the browser live. It exists so an admin can run `php artisan …`, `composer`, migrations, and quick file/debug commands against production without needing the Railway CLI on hand.

## Why this shape (and not SSH / ttyd)

The admin panel already runs *inside* the Railway app container, so "SSH into the current Railway session" is really "exec a command in the process space I'm already in" — no SSH needed. A true interactive terminal (ttyd + PTY) was rejected because it needs a second long-running process and a second port, while Railway publishes only one port per service and the web-server config is generated by railpack — i.e. it fights the "keep boot-time behaviour simple" rule in [railway-and-runtime.md](railway-and-runtime.md). So this is a one-shot, request/response streaming exec page that lives entirely within the existing PHP web process.

**Trade-off:** there is no pseudo-terminal. Interactive programs (`vim`, `top`, `php artisan tinker`) won't work. For those, use `railway ssh` from your own terminal — that gives a real TTY into the deployment with zero infra.

## How it works

- `GET /admin/shell` → `Admin\ShellController@index` renders `studio/admin/shell.blade.php` (a styled `<pre>` console + command input).
- `POST /admin/shell/run` → `Admin\ShellController@run` validates the command, **audit-logs it first**, then returns a chunked `StreamedResponse`. The browser reads the body via `fetch` + `ReadableStream` and appends each chunk into the `<pre>`, auto-scrolling.

> The console is a plain `<pre>`, not xterm.js — xterm's FitAddon mis-sized itself inside the nested HTMX studio layout (it computed a giant width before the container had real dimensions, forcing horizontal overflow). A width-constrained `<pre>` avoids all of that and needs no CDN.
>
> Layout note: `.ll-shell` is a CSS grid, so its children carry `min-width: 0` — without it the `<pre>` forces a grid track wider than the viewport (grid items default to `min-width: auto`), which pushes the whole content column left under the studio sidebar. This is the same `minmax(0, …)` trick the Dev Tools page uses.

**Favourites:** the page has a Favourites bar (saved commands as removable chips). Saved in `localStorage` (`ll_shell_favourites`, per-browser — not server-side). Clicking a chip runs that command immediately; the `×` removes it. Type a command into the Favourites input + Save to add one.
- Execution: `proc_open(['bash','-lc',$command], …, base_path())` with stderr merged into stdout, polled every 50ms, hard-killed after **120s** (`ShellController::TIMEOUT`).

## Guardrails

- **Auth:** the existing `admin` middleware (`role == 'admin'`) — same gate as the env editor / advanced-config file editor. *Note: this is the legacy role column, not the additive role system; deliberately broad per the owner's choice.*
- **CSRF:** standard Laravel token on the POST.
- **Audit:** every command is written to the dedicated `shell` log channel **before it runs** — `storage/logs/shell.log` (daily, 90-day retention), recording user id/email/name, IP, and the command. See `config/logging.php`.
- **Timeout:** 120s per command.

## Files

- `app/Http/Controllers/Admin/ShellController.php`
- `resources/views/studio/admin/shell.blade.php`
- `config/logging.php` — `shell` channel
- `routes/web.php` — `admin.shell`, `admin.shell.run`
- `app/Http/Livewire/StudioNavigation.php` — "Shell" nav entry under Admin

## Operational notes

- `proc_open` / `bash` must be available in the container (they are in the railpack PHP image). If `proc_open` is disabled, the page reports it instead of running.
- Output may contain secrets (env values, keys). The page is admin-only and `no-store`, but treat the rendered output accordingly.
- No third-party JS — the console is a self-contained `<pre>` + a small inline streaming script.
